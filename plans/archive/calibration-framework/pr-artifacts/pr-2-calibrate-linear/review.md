## Step 1 — Convergence check

### Spec coverage gaps (test-spec E19, E20, E21 missing)

The spec defines three error paths with no corresponding validation rows in
`audit.md §Per-Test Result Table`:

| Spec # | Error class | Audit result |
|--------|-------------|--------------|
| E19 | `surveywts_error_bounds_invalid_calibration` (length != 2) | MISSING |
| E20 | `surveywts_error_bounds_invalid_calibration` (NA value) | MISSING |
| E21 | `surveywts_error_calibration_not_converged` (tight bounds) | MISSING |

The audit correctly identifies these as gaps and documents them honestly. The
error classes are implemented in `.validate_bounds()` and `.calibrate_nr_engine()`
(PR 1 code). The missing tests are a builder gap: the tester did not write the
required `expect_error(class=...)` + snapshot tests for these paths.

### Quality gate 7 assertion too weak (EC11)

The spec quality gate 7 states: "assert `expect_equal(obj@calibration$n_iterations, 1L)`"
for plain linear and the impl plan acceptance criterion AC10 says "assert
`n_iterations > 1L`" for `bounds != NULL` with non-trivial targets.

The test file EC11 asserts `n_iterations >= 1L`. This is satisfied by
`n_iterations == 1L` (a single-step linear solve that happened to converge
without iterating) and does not prove that truncated-linear actually iterated.
The NR engine returns `n_iterations == 1L` when it converges in one step,
which can happen with well-conditioned data for small-perturbation bounds.
The spec requires `> 1L` to prove the iteration loop ran.
