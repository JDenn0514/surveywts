#### Section: PR 1 — Infrastructure

**Issue 9: `.to_svyrep_design()` must pass `combined.weights = FALSE` — default is `TRUE`, stored values are scale factors**
Severity: BLOCKING
Violates the "explicit over clever" principle (`engineering-preferences.md`) and the Acceptance Criteria lens (unverifiable implementation criterion that will produce silently wrong results).

`survey::svrepdesign()` defaults to `combined.weights = TRUE`. But surveywts stores replicate weights as **scale factors** (not combined sampling weights). Verification from the actual codebase:

```
Bootstrap combined.weights: FALSE
JK1 combined.weights:      FALSE
survey::svrepdesign() default: combined.weights = TRUE
```

The flow:
1. `svrep::as_bootstrap_design()` / `survey::as.svrepdesign()` return `svyrep.design` objects with `combined.weights = FALSE` — the `$repweights` matrix contains scale factors (e.g., `0`, `1.01`, `3.03`), not full sampling weights.
2. `.convert_and_call()` stores these scale factors verbatim via `as.matrix(svyrep_obj$repweights)`.
3. `.to_svyrep_design()` must reconstruct a `svyrep.design` from these stored scale factors. The plan's step 5 does not pass `combined.weights` at all, so the default `combined.weights = TRUE` is used.
4. With `combined.weights = TRUE`, `survey::svrepdesign()` interprets the scale factors as full sampling weights. `svrep::calibrate_to_sample()` then calibrates using wrong weight values.
5. The calibration constraints test (`abs(sum(w_new * X) - target) < 1e-8`) still passes numerically (svrep converges to something), but the calibrated weights are wrong relative to the true sampling design.

The fix is one argument: add `combined.weights = FALSE` to the `survey::svrepdesign()` call in step 5.

Options:
- **[A]** Add `combined.weights = FALSE` explicitly to the `survey::svrepdesign()` call in PR 1 step 5. Add an explanatory comment: the stored repweights are scale factors (not combined sampling weights) because `svrep::as_bootstrap_design()` and `survey::as.svrepdesign()` both set `combined.weights = FALSE`. — Effort: low, Risk: low, Impact: prevents silently wrong calibration
- **[B]** Add a verification substep: "Run `design_obj$combined.weights` on the reconstructed `svyrep.design` and confirm it matches the source design's value, then adjust the call accordingly." — Effort: low, Risk: medium (adds runtime check instead of fixing the root cause)
- **[C] Do nothing** — implementer uses the default `combined.weights = TRUE`; calibration produces wrong weights; tests pass; the bug is discovered in production

**Recommendation: A** — This is a one-argument fix with a clear factual basis. Option B is overly defensive when the answer is already known.

**Issue 5: Step 8c.9 `glm()` formula construction is inconsistent with the Notes**
Severity: REQUIRED
Violates the "explicit over clever" principle; the step as written produces broken code.

Step 8c.9 shows:
```r
model <- stats::glm(update(formula, response_status_vec ~ .), ...)
```
`response_status_vec` here is a bare symbol, not a string. `update.formula()` takes a formula as its second argument; writing `response_status_vec ~ .` would attempt to evaluate `response_status_vec` as a name, not substitute the actual column name (e.g., `"responded"`). This produces a formula with a literal symbol `response_status_vec` on the LHS, which `glm()` will then fail to resolve.

The Notes section correctly identifies the fix: `update(formula, paste(resp_col, "~ ."))` or explicit formula construction. The step and the Note contradict each other. An implementer reading only the step will write broken code.

Options:
- **[A]** Replace step 8c.9's `update()` call with the correct form:
  ```r
  model <- stats::glm(
    stats::as.formula(paste(resp_col, "~", deparse(formula[[2]]))),
    family = stats::binomial, data = plain_df, weights = weights_vec
  )
  ```
  or equivalently `update(formula, stats::as.formula(paste(resp_col, "~ .")))`. Sync the Note to match the step. — Effort: low, Risk: low, Impact: prevents runtime formula error
- **[B]** Remove the step's formula form and rely solely on the Notes to guide the implementer. — Effort: low, Risk: medium (Notes are advisory; step-level instructions are followed first)
- **[C] Do nothing** — implementer encounters an error at `glm()` and traces it back

**Recommendation: A** — Fix the step directly; this is a copy-paste error, not a design decision.
